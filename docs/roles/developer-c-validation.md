# 개발자 C 역할 계획: 검증·테스트

- 브랜치: `dev-c`
- 한 줄 요약: 이 앱이 내놓는 등급이 실제 위험과 맞는지 확인하고, 실제 기기와 사람으로 화면을 검증한다.
- 상대: 개발자 A는 위험도를 계산하고(`developer-a-data-risk.md`), 개발자 B는 지도와 화면을 만든다(`developer-b-map-ui.md`).
- 제품 요구사항 전문: `docs/prd.md`

## 요구사항 재정리

PRD의 로드맵에는 단계마다 통과해야 하는 게이트가 있다. A와 B가 만들기를 맡고, C는 그 게이트를 통과했는지 판정할 근거를 만든다.

| 게이트 | 통과 기준 | C가 할 일 |
| --- | --- | --- |
| 1. 지형 점수 | 표본 포인트의 점수가 현장·사진 검토와 일치 | 표본 10곳을 위성 사진·현장 사진으로 검토 |
| 2. 등급 타당성 | 과거 사고 사례의 80% 이상이 '주의' 또는 '위험'으로 재현 | 사고 사례 수집과 재계산 |
| 3. 성능 | 휴대폰에서 지도 조작 가능까지 4초 이내, 끊김 없음 | 실제 휴대폰 측정 |
| 4. 사용성 | 처음 쓰는 사람이 3번 이하 조작으로 위험 원인 확인 | 사용자 5명 관찰 테스트 |

## 소유 경로

| 경로 | 내용 |
| --- | --- |
| `validation/` | 사고 사례 데이터, 재계산 스크립트, 측정 결과 |
| `tests/e2e/` | 브라우저 자동 테스트 |
| `docs/validation/` | 검증 보고서 |

그 밖의 경로는 읽기만 한다. 계산식(`lib/risk/`)이나 화면 코드에 문제가 보이면 직접 고치지 않고 `docs/api-contract.md`의 "요청" 섹션에 적는다.

## 단계별 계획

### 0단계. 준비

1. `docs/prd.md`, `CLAUDE.md`, 두 역할 문서의 "진행 기록"을 읽는다.
2. `npm install` 후 `npm run dev`로 화면을 띄워 본다. 주소에 `?demo=contract`를 붙이면 세 등급이 섞인 예시가 나온다.

- 완료 기준: 화면을 직접 조작해 보고, 등급이 어떤 입력으로 계산되는지 한 문단으로 설명할 수 있다.

### 1단계. 사고 사례 수집 (게이트 2의 재료)

1. 오리건주 링컨 카운티 해안의 낚시·해안 사고를 모은다. 출처는 지역 언론, 해안경비대·보안관실 발표, 미국 기상청 자료다.
2. `validation/incidents.csv`에 적는다. 열: 날짜, 시각(현지), 위도, 경도, 장소 유형, 사고 유형, 출처 주소, 비고.
3. 시각이나 위치가 불분명한 사례는 버리지 말고 비고에 불확실한 정도를 적는다.

- 완료 기준: 20건 이상. 20건을 못 구하면 구한 만큼으로 진행하고 그 사실을 보고서에 적는다.
- 주의: 사고 당사자의 이름 같은 개인 정보는 적지 않는다.

### 2단계. 등급 재현 (게이트 2)

1. 각 사례의 날짜·시각·위치에 대해 과거 날씨(Open-Meteo의 과거 자료)를 받는다.
2. A의 계산 함수(`lib/risk`의 `computeHourlyRisk`)에 넣어 그 시각의 등급을 구한다. 지형 점수는 A의 결과가 있으면 그것을, 없으면 가장 가까운 포인트의 값을 쓴다.
3. 결과를 `docs/validation/gate2.md`에 표로 정리한다. '주의' 이상으로 나온 비율, 놓친 사례와 그 이유의 추정을 적는다.

- 완료 기준: 재현 비율이 숫자로 나온다. 80%에 못 미치면 어떤 요인의 가중치·임계값이 의심되는지 "요청" 섹션에 적는다.
- 검증: 재계산 스크립트를 다시 돌렸을 때 같은 결과가 나온다.

### 3단계. 실제 기기 성능과 접근성 (게이트 3)

1. 실제 휴대폰(가능하면 중급 기종)에서 지도를 연다. 브라우저 콘솔의 `performance.getEntriesByName('map-ready')[0].startTime`으로 지도 조작 가능 시점을 잰다.
2. 지도를 끌고 기울일 때 끊기는지, 시간 슬라이더를 움직일 때 느려지는지 본다.
3. 화면 읽기 프로그램과 키보드만으로 핀 선택부터 원인 확인까지 해 본다.

- 완료 기준: 기종, 통신 환경, 측정값을 `docs/validation/gate3.md`에 적는다. 에뮬레이션 측정값은 B 문서의 "검증 기록"에 있다.

### 4단계. 사용자 관찰 테스트 (게이트 4)

1. 낚시를 하는 사람 5명에게 "내일 아침 이 포인트에 가도 되는지 확인해 보라"는 과제를 준다. 사용법은 설명하지 않는다.
2. 위험 원인을 확인하기까지의 조작 횟수와 시간, 막힌 지점, 오해한 표현을 기록한다.

- 완료 기준: `docs/validation/gate4.md`에 참가자별 결과와 고칠 점 목록이 있다. 참가자의 이름은 적지 않는다.

### 5단계. 자동 테스트

1. `tests/e2e/`에 브라우저 자동 테스트를 만든다. 대상: 핀 선택 시 상세 시트 표시, 시간 슬라이더 이동 시 등급 변경, 추천 목록 표시, 데이터 지연·오류·지원 범위 밖 상태.
2. 날씨에 따라 결과가 달라지지 않도록 `?demo=contract` 같은 고정 예시를 쓴다.

- 완료 기준: `npm run test:e2e`가 통과한다. 테스트 도구 추가는 의존성 변경이므로 `CLAUDE.md`의 공유 파일 규칙을 따른다.

## A, B와 주고받는 것

| 상대 | C가 주는 것 | C가 받는 것 |
| --- | --- | --- |
| A | 놓친 사고 사례, 의심되는 가중치·임계값 | 계산 함수, 포인트와 지형 점수 |
| B | 실제 기기에서 본 끊김, 사용자가 막힌 지점과 오해한 표현 | 화면, 상태 확인용 주소 |

## 위험 요소

| 위험 | 수준 | 대응 |
| --- | --- | --- |
| 사고 기록이 적거나 시각·위치가 불분명함 | 높음 | 구한 만큼으로 진행하고 한계를 보고서에 적는다. 기준을 낮출지는 사용자와 정한다 |
| 과거 날씨 자료의 해상도가 낮아 사고 당시 상황과 다름 | 중간 | 가까운 관측소(NOAA South Beach)의 실측과 비교해 차이를 적는다 |
| 사용자 테스트 참가자를 못 구함 | 중간 | 3명으로 줄여 진행하고 그 사실을 적는다 |
| 검증 결과가 A·B의 일정과 어긋남 | 낮음 | 결과는 "요청" 섹션으로 전달하고 직접 고치지 않는다 |

## 복잡도

중간. 사고 사례 수집(1단계)이 가장 오래 걸리고 결과가 불확실하다.
